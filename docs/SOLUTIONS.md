# OV2640 + ESP32-S3 — 问题与解决方案（工程复盘）

> 本文档系统性记录开发中遇到的实际问题、根因诊断与最终解决，按**问题域**分类，含结论可直接复现。
> 体系结构见 [ARCHITECTURE.md](./ARCHITECTURE.md)。论文可直接引用本节作为实验结果与设计取舍依据。

## 一、硬件层

### H1. GPIO11/12 物理损坏 → DVP 数据位恒 0，花屏
- **现象**：RGB565 字节序已修正，仍出现"结构完整但颜色坏"的伪彩。
- **诊断**：`host/diagnostics/diag_stripes.py` 做**位级激活率统计** —— 对每根数据位统计 0/1 翻转率，发现某几位 **0% 激活**（恒 0），确认是断线而非软件。
- **解决**：**D0 原 GPIO11 → 改接 GPIO1；D4 原 GPIO12 → 改接 GPIO2**，并更新固件脚位宏，花屏消失。
- **教训**：花屏/彩带先查数据位激活率，再动寄存器；字节序与坏数据线是两个**独立**根因，须都修好才出正常图。

### H2. OV2640 大端输出 → 上位机必须 big-endian 解析 RGB565
- **现象**：RGB565 画面被解码成大片色带/伪彩。
- **根因**：OV2640 按 **big-endian**（高字节在前）输出，上位机误用 little-endian。
- **解决**：`v = (frame[o] << 8) | frame[o+1]`。这是维护中**最常被误改回**的一处。

### H3. 定焦镜头无法对焦 → "模糊"是误判
- OV2640 无对焦电机。预览 QQVGA(160×120) 被放大显示显得糊，切 QVGA 即清晰；近距离(<20cm)物理模糊正常。非故障。

### H4. 曝光/快门控制（拍星不可行）
- OV2640 的曝光由帧周期决定，30fps 下最多几十 ms 量级，**无法做秒级长曝光**，因此**无法拍星空**。该传感器在相机设计上定位为近距离/文档拍摄；拍星须换长曝光 CMOS或天文相机。仅保留 `set_exposure_ctrl`/AEC/增益作夜景微调，对星无帮助。

## 二、固件/采集层

### F1. JPEG 空帧 bug（FB-OVF）→ 从源码编译 esp32-camera
- **现象**：RGB565 出图正常，切 JPEG 后 `esp_camera_fb_get` 返回空帧，报 `FB-OVF`。
- **根因**：Arduino 预编译库 `libespressif__esp32-camera.a` 对 JPEG 的 SOI(FFD8) 起始标记校验过严，OV2640 输出不满足其内部断言 → 整帧被丢弃。
- **解决**：PlatformIO `lib_deps = espressif/esp32-camera` **从源码编译**（非预编译 `.a`），绕开该校验。工程 `esp32s3_camera_pio`。

### F2. 帧缓冲 PSRAM OOM + `set_framesize` 重配缺陷
- **现象**：从低分辨率切高分辨率（VGA/SVGA/UXGA）`fb_get` 一直空、失锁。
- **根因**：预编译库在 PSRAM 下 `set_framesize` 未真正重配 DMA 缓冲；写死 `fb_count=2` 在 UXGA(3.84MB×2≈7.7MB) 时 OOM。
- **解决**：
  1. 切换一律走 **`deinit + init` 全量重配**；
  2. `fb_count_for()` 按分辨率自适应缓冲（大图单缓冲），预留 6MB；
  3. `init_camera_as` 失败自动降级（双缓冲→单缓冲→fallback 分辨率），绝不死锁；
  4. 连续 2 次抓帧失败触发 `camera_reconnect()` 重建。

### F3. 运行时切 VGA 触发 EV-VSYNC-OVF 死循环
- esp32-camera 库残留 bug：运行时经寄存器路径切 **VGA** 会进入 EV-VSYNC-OVF 死循环。因此 **VGA 必须设开机默认**，运行时由低切高一律走全量 deinit+init。

### F4. 分辨率切换的快速路径（2026-09 新增）
- **问题**：所有切换都走 deinit+init 全量重建，约 **0.5~1s 黑屏/冻结**，成本高。
- **优化**：QQVGA↔QVGA（CIF 系、fb_count=2、缓冲开机按大图分配）走寄存器级 `sensor->set_framesize`，**毫秒级**；涉及 VGA 及以上仍走慢路径（避 F3 / 需重分配缓冲）。
- **实测**：切换瞬间最大停顿从 ~1s 降到 **~130ms**（QVGA 回切）；中继模式下分辨率切换此前失效，现也能正常生效。（`deploy/test_switch.py` 复测）

### F5. 采集必须固定核1，网络任务固定核0
- 采集固定在核1（`-DCONFIG_CAMERA_CORE1`）：切换分辨率 deinit 跨核与 cam_task 拷贝并发，释放 cam_obj → use-after-free 卡死。
- 网络任务（sender/relay/disc）固定在核0：避免抢占核1 实时采集/控制。核内优先级 sender(3) > relay(1)/disc(1)。

## 三、网络/传输层

### N1. 中继 TCP 流错位（根治帧率骤降/垃圾字节/周期重连）
- **现象**：中继观看出现间歇性垃圾字节、帧率骤降、周期 5s 重连。
- **根因**：`relay_send_iov` 在 TCP 背压（`write()==0`）时**发送 4 字节长度头后中途放弃消息**，导致长度前缀流永久错位 —— 服务端把后续所有帧的字节误读成这一条的巨型净荷，直到 45s 超时或重连才恢复。
- **解决**：改为**循环重试发送完整消息**（背压等待缓冲腾空再发），阻塞超过 ~2s 才 `relay_cli.stop()` 主动断开重建干净流。
- **复用规则**：长度前缀协议下，`写长度头 + 写净荷` 是一个原子事务，**严禁中途放弃**。

### N2. 多客户端"抢占式"接管导致互相顶帧
- **现象**：多个预览进程同时连接同一摄像头 → 画面卡顿、帧率忽高忽低、新连接顶掉旧连接。
- **机制**：固件 loop() 对 TCP 采用**抢占式 accept** —— 即使旧客户端仍 `connected()`，新连接也接管并 `stop()` 旧的。
- **规避**：一台摄像头同一时刻只用一个观看进程（尤其别同时跑多个 `live_capture.py`/`relay_fps.py`）。排查用 `Get-CimInstance Win32_Process` 按命令行匹配清理。

### N3. WiFi TX 队列满（ERR_MEM）→ 分帧大小差异化重试
- **现象**：DIAG `err=-1`（lwIP ERR_MEM = netif TX 队列满），QQVGA 丢片 2%、VGA 掉到 5fps；1ms×3 短重试几乎不恢复。
- **结论**：链路/射频争用所致（`pbf=0` 排除内存不足，AEC/AGC 正常），非编码或曝光问题。
- **解决**（按帧大小分策略）：
  1. **小帧 ≤4 片**（QQVGA/QVGA）：每 2ms 轮询重试同分片，最长等 12ms → 丢包率 2%→0，QQVGA 25→29.4fps。
  2. **大帧 >4 片**（VGA/SVGA）：只 1ms 短重试，不阻塞采集流水线（否则多片各自 12ms 反而饿死发送）；持续失败丢帧 + 背压 3 帧排空。
- **倾向**：小分辨率已到传感器上限且零丢片；SVGA 受 2.4GHz 信道容量限于 ~2-6fps。

### N4. 流媒体期间关软AP释放空口
- WiFi 关 modem sleep 能消除每包唤醒延迟；流媒体期间 `softAPdisconnect()` 释放空口给 STA（同信道），VGA 容量近乎翻倍（4.9→14.9fps）。热点兜底模式下不可关（关即断流）。

### N5. UDP 分片背压与自适应 JPEG 质量
- UDP TX 队列满会 `ERR_MEM` 丢包，按帧大小实施重试策略（见 N3）。
- **自适应画质**：以"发送队列被顶帧数 `g_adapt_total_evict`"替代单纯丢包 `err_delta` 作为拥塞信号（中继无 UDP err），带宽不足时自动加大 JPEG 压缩、回剥中继目标帧率（QVGA 12→20fps）。修复了首帧基线未初始化 `g_adapt_last_evict` 导致不生效的 bug。

### N6. P2P 打洞/TURN 策略
- 传统打洞，公开端点交叉撮合；对称/端口受限 NAT 失败时 **5s 超时降级 TURN**，再失败回退 TCP 中继。客户端一次打洞失败即本会话禁用 P2P，避免"打洞失败→重连→再打洞"死循环破坏正常 TCP 推流。
- 当前**稳定可靠路径 = 纯 TCP 中继（不带 `--p2p`）**。

### N7. 2.4GHz 信道拥挤是外部波动，非固件退化
- 同一配置安静/拥挤时段帧率差异显著。当邻居路由器争用当前信道时，DIAG 持续报 `uerr 攀升 / err=-1(TX 队列满)`。固件链路容量已用尽；想要稳定可换空闲信道（热点固定 ch6）。

## 四、上位机/集成层

### P1. RGB565 big-endian 解析（同 H2，验收基准）
- 统一 `(frame[o]<<8)|frame[o+1]`；格式随帧头 `SIZE <w> <h> <JPG|RGB>` 携带。

### P2. 三级自动重连（兜底裸板触碰短路复位）
1. 串口读异常 → 关闭并自动重开；2. 超过 `RECONNECT_AFTER=5s` 无帧 → 强制重开；3. 重开后首帧触发 `resync_board()` 重新下发 `V/H` 分辨率，使板端与界面对齐（MCU 复位丢运行时设置）。

### P3. 最新帧优先 + 实时帧率
- 预览队列 `maxsize=2` + `put_latest()`（满丢最旧）保证渲染永不滞后；滑动窗口每秒结算帧率，界面底部实时显示 —— 帧率数字与实际观感一致。

### P4. 串口占用 PermissionError(13)
- 多个残留 python 进程占用 COM 口。用 `Get-CimInstance Win32_Process` 按 `CommandLine` 匹配 `live_capture` 并 `Stop-Process` 结束。

### P5. 色彩看门狗（根治偶发蓝紫偏）
- 源码版 esp32-camera 的 `set_wb_mode` 写入的 DSP 寄存器表与本 OV2640 模块不兼容，偶发 UV 增益损坏且 API 无法回写恢复。
- 上位机内置看门狗：B 显著高于 R/G 持续 3s → 自动下发 `r` 完整重建，~5s 自愈。`set_whitebal`/`set_awb_gain` 需同时置 CTRL1 bit3+bit2 AWB 才生效。

## 五、通用方法论

- **先定位瓶颈域再做优化**：板载 DIAG（采集速率/发送速率/丢片率/RSSI/错误码）一眼区分"编码瓶颈 / 链路瓶颈 / 曝光拉长"。
- **位级/采样级诊断优先**：花屏先查数据位激活率，颜色先查 8bit 采样（勿用 6bit），再动寄存器。
- **长度前缀协议严禁中途放弃消息**；**多客户端互斥**；**改字节序/引脚务必双写文档**。
