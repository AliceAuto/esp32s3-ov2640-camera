# OV2640 + ESP32-S3 选型论证

> 本文档从**系统需求**出发，论证图像传感器与主控芯片的选型依据，是本系统设计的第一性依据。
> 体系结构见 [ARCHITECTURE.md](./ARCHITECTURE.md)，问题复盘见 [SOLUTIONS.md](./SOLUTIONS.md)。

---

## 1. 系统需求约束（选型的出发点）

在选型前先固化系统约束，选型结果必须全部满足，而非先定器件再迁就：

| 需求 | 量化约束 |
|------|----------|
| 实时视频采集 | 预览 ≥ 15fps，局域网小分辨率跑满传感器上限（30fps） |
| 分辨率档位 | 至少 6 档，最高 UXGA 1600×1200 供高清拍照 |
| 图像压缩 | **板端硬件 JPEG**，避免软压占用主控算力 |
| 帧缓冲 | 高分辨率单帧 ≥ 3.8MB（UXGA RGB565），必须有片外大容量 RAM |
| 无线传输 | 2.4GHz 局域网 + 跨网中继，需板载 WiFi |
| 成本 / 体积 / 功耗 | 面向嵌入式量产级，低成本、低功耗、小尺寸 |
| 开发效率 | 生态成熟、资料丰富、社区方案多 |

## 2. 图像传感器选型：OV2640

### 2.1 需求聚焦
满足【1】需三要素缺一不可：**分辨率足够（高）、内置 JPEG 编码（省算力）、DVP/CCIR 并行接口（对接 MCU）**。

### 2.2 候选对比

| 指标 | **OV7670** | **OV2640（选用）** | **OV5640** |
|------|-----------|-------------------|-----------|
| 最大分辨率 | VGA 640×480 | **UXGA 1600×1200**（2MP） | 5MP 2592×1944 |
| 内置 JPEG | 无（需软压） | **有（硬件压缩）** | 有 |
| 输出接口 | DVP | DVP/CCIR | DVP / MIPI CSI |
| 功耗 | 低 | 百 mW 级 | 较高（发热明显） |
| 成本 | 低 | **低** | 较高 |
| 驱动复杂度 | 低 | 低（社区/官方例程多） | 高（寄存器多、时序复杂） |
| 与 ESP32 生态契合度 | 中 | **高（esp32-camera 原生支持）** | 中 |

### 2.3 选择理由（对号入座）
1. **分辨率与压缩兼得**：UXGA 2MP 满足"6 档分辨率 + 高清拍照"，且**内置硬件 JPEG**——直接把 3.8MB 原始像素压到几十 KB，主控几乎零算力参与编码，这是 UDP/TCP 高帧率传输的前提。
2. **接口匹配**：DVP 并行接口可直接接入 ESP32-S3 的摄像头控制器（CAM），硬件帧同步，无需外部时序芯片。
3. **生态成熟度**：`esp32-camera` 官方库对该型号支持最好，社区例程与文档最全，显著降低开发风险。
4. **成本功耗**：属低端量产型号，价格低、发热小，契合嵌入式量产定位。

### 2.4 已知局限与影响（诚实记录，作为论文讨论项）
| 局限 | 影响 | 应对/取舍 |
|------|------|-----------|
| **定焦镜头，无对焦电机** | 近距(<20cm)与低分辨率放大后"模糊" | 预览用 QVGA；拍摄按文档/实物目标定焦（见 SOLUTIONS H3）|
| **无长曝光能力** | 曝光电帧周期决定，30fps 下最多几十 ms | 无法拍星空，传感器定位为近距/文档拍摄（见 SOLUTIONS H4）|
| **AWB 寄存器表兼容问题** | 源码版 esp32-camera 偶发 UV 增益异常 | 上位机色彩看门狗自动重建自愈（见 SOLUTIONS P5）|

> 局限并非选型错误，而是该档位传感器的**物理边界**，已在需求阶段接受并在软件层兜底。

## 3. 主控芯片选型：ESP32-S3

### 3.1 需求聚焦
满足【1】需主控具备四要素：**DVP 摄像头接口、片外 PSRAM（大帧缓冲）、板载 WiFi、足够算力（双核）**。

### 3.2 候选对比

| 指标 | STM32H7 | **ESP32 原版** | **ESP32-S3（选用）** | ESP32-C3/C6 |
|------|---------|---------------|---------------------|-------------|
| 内核 | Cortex-M7 480MHz | 双核 LX6 240MHz | **双核 LX7 240MHz** | 单核 RISC-V 160MHz |
| PSRAM 友好 | 支持但接口较弱 | SPI RAM（性能一般） | **8MB OPI Octal PSRAM** | 不支持 PSRAM |
| 板载 WiFi | 无（需外挂芯片） | 有 2.4GHz | **有 2.4GHz + BLE5** | 有（2.4GHz，C6 为 WiFi6） |
| 摄像头接口 | 需外扩 FMC/DCMI | 无专用 | **CAM 控制器支持 DVP** | 无 |
| 典型成本 | 高 | 低 | **低** | 低 |
| 生态 | 老牌丰富 | 极高 | **极高（esp-idf/Arduino）** | 高 |

### 3.3 选择理由（对号入座）
1. **8MB OPI PSRAM —— 决定性的选择**：UXGA RGB565 单帧 3.84MB，双缓冲 7.7MB，**只有 8MB 片外 PSRAM 能承载**。这是本项目区别于 STM32 平台的核心原因——高分辨率帧缓冲必须落位 PSRAM 而非内部 SRAM（内部仅 520KB）。
2. **DVP 摄像头接口**：ESP32-S3 内置 CAM 控制器，可直接对接 OV2640 的 DVP 并行输出，硬件完成像素采集与 DMA，无需胶合逻辑。
3. **双核异构调度**：本项目正是利用双核做**采集核1 / 网络核0 分离**（见 ARCHITECTURE §3.1），网络发送不抢占实时采集，这是跨网帧率稳定的硬件基础。
4. **板载 WiFi + 低功耗**：单芯片集成 RF，省去外置 WiFi 模块的成本与体积，符合嵌入式低功耗量产定位。
5. **原生 FreeRTOS + 生态**：esp-idf/Arduino 之上即 FreeRTOS，任务/队列/信号量开箱即用；`esp32-camera` 官方例程原生支持 S3，缩短开发周期。

### 3.4 已用到的关键能力（与系统设计一一对应）
| S3 能力 | 系统内用途 |
|---------|-----------|
| 8MB OPI PSRAM | 帧缓冲池 + `fb_count_for()` 自适应缓冲（见 SOLUTIONS F2）|
| 双核 FreeRTOS | 采集核1 / 网络核0 任务亲和（见 ARCHITECTURE §3.1）|
| CAM 控制器 | OV2640 DVP 像素采集 |
| 内置 WiFi | STA/AP，TCP-UDP/中继 传输 |
| WiFi 省电与空口调度 | modem sleep 关断 + 流媒体期间关软 AP 放空口（见 SOLUTIONS N4）|

## 4. 传感器 × 主控 协同论证

- **接口匹配**：OV2640 的 DVP + ESP32-S3 的 CAM 构成硬件即插即用链，帧同步由硬件完成，软件只做帧调度。
- **算力分工**：OV2640 完成 **JPEG 硬件压缩**，ESP32-S3 专注 **采集调度 + 传输 + 控制**，两者互补不争算力。
- **内存协同**：8MB PSRAM 既承载大分辨率帧缓冲，也容纳"丢旧保新"发送队列，支撑实时流水线（见 ARCHITECTURE §3.2）。

## 5. 选型小结

| 维度 | 结论 |
|------|------|
| 图像传感器 | **OV2640** —— 分辨率/硬件JPEG/DVP/成本/生态五者平衡 |
| 主控 MCU | **ESP32-S3** —— 8MB PSRAM + DVP接口 + 双核 + 板载WiFi，缺一不可 |
| 组合匹配 | DVP 硬件直连 + 算力/内存分工，构成完整实时视频链路 |

> 选型在**需求约束**驱动下完成：先固化"高分辨率帧缓冲 + 硬件压缩 + 双核调度 + 板载无线"四约束，再让器件对号入座，而非先有器件再迁就需求。这是本项目的设计第一性来源。
